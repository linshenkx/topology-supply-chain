# 生产门禁

## 1. 当前判定

| 判断 | 当前状态 | 说明 |
| --- | --- | --- |
| 本地可运行/展示 | 有基础 | 已有前端和预览运行方式，但部分页面使用静态数据 |
| 可做开发集成 | 有条件 | 需要先稳定 Windows 开发命令和真实 MySQL 测试环境 |
| 可做完整业务 UAT | 未达到 | 主链在生产质检放行、真实领料/预留、正式导入处断开 |
| 可开放生产流量 | **No-Go** | 存在身份冒充、Step-up 绕过、审批/库存/付款一致性等 P0 |

生产门禁采用“证据通过”而不是“代码存在”。完整生产发布要求全部 P0 关闭；隔离开发环境可以继续搭建底座，但任何真实入口、外部 UAT 或领域切写都必须先关闭其作用域内 P0。

## 2. 严重级别

| 级别 | 定义 | 允许的环境 |
| --- | --- | --- |
| P0 | 可导致身份冒充、越权、资金/库存错账、不可恢复迁移或主链断裂 | 允许隔离开发；禁止受影响真实入口、外部 UAT 和生产切流 |
| P1 | 首批真实业务会遇到的数据隔离、文件、通知、观测、恢复或兼容缺陷 | 可做受控开发/UAT；生产前必须关闭或获书面风险接受 |
| P2 | 不立即破坏正确性，但会降低维护、合规、性能或长期演进能力 | 可进入后续里程碑，但需责任人和期限 |

风险接受不能用于绕过身份冒充、资金/库存错误、数据不可恢复等 P0。

P0 按门禁作用域关闭，避免“阶段 2 前全部清零、但阶段 6 才修业务闭环”的循环：

| 门禁点 | 必须关闭 |
| --- | --- |
| 阶段 2 隔离底座入口 | SEC-001；MIG-001 生产基线；DATA-001 对底座的真实 MySQL 路径；DEP-001 临时关闭；仍开放 legacy 写入口对应的 SEC-002/AUTHZ-001/CONSISTENCY-001 |
| 任一 v1 领域首次切写 | 该领域全部安全、授权、并发、数据与业务闭环 P0；MIG-002 writer fence |
| 阶段 6 实物链切写 | BIZ-001、BIZ-002、BIZ-003 全部关闭 |
| 完整生产发布 | 本清单全部关闭，且发布评审表全绿 |

## 3. 当前 P0 清单

### SEC-001 外部身份头可伪造

- 证据：`app/lib/authz.ts:38-57` 在无 Session 时信任 `oai-authenticated-user-email`；`deploy/aliyun/nginx-scm.conf:38-48` 未清除该头。
- 完成标准：生产路径彻底禁用 fallback；Nginx 清空身份断言头；从真实入口发送伪造头仍返回 401；本地预览必须由显式环境开关且只绑定回环。

### SEC-002 财务 Step-up 可由客户端布尔值绕过

- 证据：`app/api/finance/route.ts:98-100,294-316,498-500`。
- 完成标准：业务接口只接受一次性 proof/challenge 标识；服务端验证并在业务事务中消费；跨用户、跨会话、跨动作、跨对象、过期和重放全部失败。

### AUTHZ-001 审批策略与职责分离不完整

- 证据：`app/api/approvals/route.ts` 对多种 workflow 的查看/审核角色不完整，且部分路径先更新审批再检查后续权限。
- 完成标准：每个 workflow 有枚举化策略；权限检查在任何写入前完成；发起人不能自审；并发审核只有一个成功；审批状态、业务副作用和审计 Outbox 原子提交。

### CONSISTENCY-001 调拨/发货/付款并发可重复或超额

- 证据：`app/api/inventory/transfers/route.ts:60-96`、`app/api/shipments/route.ts:221-370`、`app/api/finance/route.ts:508-531`。
- 完成标准：相同命令重放得到同一结果；并发 2/10/50 次只有一次有效状态转换；库存不为负、发货不重复、请款不重复、已付不超额；数据库唯一约束和原子条件共同兜底。

### DATA-001 D1/MySQL 方言与类型不一致

- 证据：`db/index.ts:24-28` 强制类型转换；`app/api/auth/verify/route.ts:21-28` 使用 SQLite 风格 Upsert。
- 完成标准：核心代码以真实 MySQL 类型编译；MySQL 8 集成测试覆盖登录和全部关键写路径；禁止通过类型断言隐藏方言差异。

### MIG-001 生产 Schema 与迁移历史不可信

- 证据：`PROJECT_STATUS.md:250-259` 记录业务表、迁移记录和 DMS 人工修正曾不一致；现有回滚脚本只回应用。
- 完成标准：生产 Schema 快照、迁移历史、人工变更三方对齐；空库和生产副本可重复升级；旧/新应用均兼容 Expand 阶段；完成备份恢复和应用回切演练。

### MIG-002 新旧后端缺少服务端写入围栏

- 风险：仅靠前端/Nginx 切换时，旧 `/api` 仍可直调；v0 已提交但响应丢失后向 v1 重试，可产生第二笔付款、扣库、请款或审批效果。
- 完成标准：新旧处理器共同校验数据库 `writer_fence(owner, epoch)`；幂等使用与 URL 无关的 canonical command identity；blocked→排空→对账→epoch+1→v1 协议通过；旧入口在切写后返回 409/410 且无落库证据。

### DEP-001 可触达高危依赖与不受限 Excel 解析

- 本次基线审计记录：`pnpm audit --prod --json` 返回 11 个 high、8 个 moderate、0 critical；该数字会随公告变化，实施时必须重跑并保存报告。
- 证据重点：`xlsx 0.18.5` 固定在 `package.json`，上传文件在 `app/api/imports/preview/route.ts:23-26` 的请求进程直接解析。
- 临时关闭标准（阶段 1）：不可信 Excel 上传入口关闭，或仅由受控管理员在与 Web 进程隔离的环境离线处理；不得继续公网请求内解析。
- 永久关闭标准（导入启用前）：可触达 high 清零，或有经安全负责人批准且带补偿控制/期限的例外；解析移入资源受限 Worker，具备大小、行列、时长、内存和恶意内容限制。

### BIZ-001 生产→质检→库存未闭环

- 证据：`app/lib/production-finalization.ts:53-75` 创建待检数量；`app/api/quality-inspections/route.ts:173-207` 只写质检结果，未释放/隔离具体库存批次。
- 完成标准：生产批次、质检任务和库存批次一一可追踪；通过、失败、部分放行、全检和处置的数量守恒；重复提交不重复释放。

### BIZ-002 BOM 领料未与真实库存闭环

- 证据：`app/api/production-orders/route.ts:84-89` 只写生产物料行的 `reservedQuantity`，未创建/消费真实库存预留。
- 完成标准：每个生产物料需求可追到库存批次预留、释放、领用、消耗和损耗流水；部分预留、缺口和并发均可解释。

### BIZ-003 采购收货/来料入库缺失

- 证据：采购、质检和库存表各自存在，但没有 Purchase Receipt 把采购明细、到货数量、来料质检和有来源的待检库存批次连接起来。
- 完成标准：Receipt 归 Procurement；重复收货不重复入账；Receipt→来料质检→待检批次→放行/隔离可追踪且数量守恒；累计收货不超允许数量，UAT-REC-01 通过。

## 4. Gate A：业务正确性

### 必须证据

- 正式角色、组织层级、数据权威和法律/财务主体已签字确认。
- `01-business-baseline.md` 中主链和异常链均有可执行 UAT。
- 采购、生产、库存、物流和财务的关键数量/金额不变量具有自动化测试。
- 所有页面标为真实/部分/演示；生产入口不能出现未接 API 却声称成功的操作。
- 历史数据迁移后，抽样与全量对账规则均通过。

### 关键对账

```text
采购：计划已分配量 ≤ 允许容差后的计划量
生产：领用 = 消耗 + 损耗 + 退料（按确定的业务规则）
库存：期初 + 入库 - 出库 ± 调整 = 期末；每个状态数量均非负
质检：批次数量 = 放行 + 隔离/待处置 + 已处置去向
发货：发货数量 = 各库存批次扣减之和 = 有效发货明细
发票：有效占用 ≤ 有效票额
付款：有效付款/退款净额 ≤ 请款可付额
```

具体容差、退料和部分放行规则仍需业务确认，不能由开发自行猜测。

## 5. Gate B：身份、权限与应用安全

### 权限矩阵测试

至少覆盖：管理员、供应链、财务、公司质检、工厂、供应商质检、收货方，以及待确认的供应链负责人/工厂管理员/供应商普通用户。

每类角色验证：

- 正常读取/写入允许的对象。
- 通过更换 URL ID、Body 中 `factoryId/supplierId`、分页和导出尝试跨组织访问。
- 角色过期、账号停用、Session 吊销、密码变更后的即时效果。
- 发起人自审、同一人多角色、两人并发审核和高风险证明重放。
- 文件下载、审计查看和导出是否遵循相同数据作用域。

### Web/API 安全

- 固定允许的 Host/Origin；状态变更请求有 CSRF 防护。
- Cookie 标志、Session 轮换、登录限流、验证码限流和账号枚举防护通过。
- Step-up grant 绑定用户、会话、动作、对象版本和 canonical request hash；金额、币种、银行引用、交易对手或日期变化会使原证明失效。
- 输入使用运行时 Schema，未知字段策略明确；内部错误不回显 SQL/堆栈。
- 文件校验真实类型、病毒/恶意内容、大小和解压资源；对象默认私有。
- 密钥扫描、SAST、依赖扫描、容器扫描、SBOM 和许可证检查进入 CI。
- 日志、Trace 和审计不记录验证码、Cookie、完整手机号、银行敏感信息或签名 URL。

## 6. Gate C：数据、迁移与恢复兼容

每个 Schema 变更必须完成：

1. **Expand**：只加兼容字段/表/索引，旧应用仍能工作。
2. **Backfill**：可暂停、可重入、可观测，记录进度和失败行。
3. **Verify**：总数、哈希/聚合、外键、非空、业务不变量和抽样对账。
4. **Switch**：新应用开始读写新结构，有明确回切条件。
5. **Contract**：旧调用归零、恢复窗口结束后才删除旧结构。

必测路径：

- 空库从零迁移到最新。
- 当前生产 Schema 副本升级到最新。
- 已执行一次后再次执行不会破坏数据。
- 新 Schema 上运行上一个兼容应用版本。
- Backfill 中断后继续。
- 失败时恢复备份并验证业务数据，而不是只验证数据库能启动。

禁止项：自动运行未经生产副本验证的破坏性 DDL；在回滚脚本中假装数据库会随应用自动回退。

每次写所有权切换还必须验证：

- 数据库 `writer_fence` 从 legacy→blocked→v1 的 epoch 变化可审计。
- blocked 期间新旧入口均拒写，旧在途请求已经排空并完成 canonical command/账实对账。
- v1 启用后旧入口稳定返回 409/410；绕过前端直接调用也不落库。
- v0 已提交但响应丢失、随后向 v1 重试时只返回同一业务结果。
- 首次 v1 写入后，若 legacy 未获兼容证明，则回滚计划只能冻结、部署兼容 v1/向前修复或执行 compensating command。

## 7. Gate D：自动化测试

| 层级 | 必须覆盖 | 运行时机 |
| --- | --- | --- |
| Domain 单元 | 金额/数量、状态机、容差、职责分离、效期、处置守恒 | 每次 PR |
| API 契约 | 请求/响应 Schema、错误码、兼容性、生成 Client | 每次 PR |
| Repository/MySQL 集成 | 真实方言、事务、锁、唯一约束、迁移 | 每次 PR |
| 权限矩阵 | 角色 × 动作 × 数据作用域 × 状态 | 每次 PR，完整集可分片 |
| 并发/幂等 | 审批、预留、调拨、发货、付款、导入 | 每次相关 PR + 发布前 |
| Worker | claim、重试、死信、重复消费、下游失败 | 每次相关 PR |
| E2E/UAT 自动化 | 主链和高价值异常链 | 合并后 + 发布候选 |
| 性能/容量 | 高峰 API、导入、导出、批处理、数据库池 | 发布候选/定期 |
| 恢复/故障 | DB/OSS/短信/邮件超时、进程退出、回滚、恢复 | 发布前/季度演练 |

当前只有 `tests/business-rules.test.mjs` 和 `tests/rendered-html.test.mjs`，远低于风险要求。

### 可复现性要求

- 每个测试套件固定 fixture/seed 版本、业务 oracle、MySQL/依赖摘要、执行命令和随机种子。
- 并发结果不仅检查 HTTP 状态，还要重算库存、金额、状态、幂等记录、Outbox 和审计。
- 报告以不可变 CI artifact 保存，release manifest 记录 SHA-256、运行环境、Git SHA 和批准人。
- UAT 保留脱敏输入、操作人/角色、时间、响应、数据库/流水对账、缺陷号和业务签字。
- 无法重复执行或只有截图、没有 oracle 的结果不能把门禁改为绿色。

## 8. Gate E：CI/CD 与制品

推荐流水线顺序：

```text
锁文件安装
  → lint + format check + typecheck
  → domain/unit tests
  → OpenAPI/client drift check
  → MySQL migration + integration + permission/concurrency tests
  → dependency/SAST/secret/license scan
  → build Web/API/Worker
  → container scan + SBOM + sign
  → deploy UAT
  → smoke/E2E/UAT evidence
  → production approval
  → canary/rolling deploy
  → post-deploy probes + rollback guard
```

制品要求：

- 镜像不可变，以 Git SHA/摘要标识，不使用会漂移的 `latest` 作为发布凭据。
- 发布记录关联代码提交、OpenAPI 版本、数据库迁移、配置版本、SBOM 和审批人。
- 生产服务器只拉取已验证制品，不现场构建源码。
- Web/API/Worker 分别发布，但必须声明兼容矩阵。
- 迁移、发布和回滚脚本非交互、可审计、失败即停。

## 9. Gate F：可观测性

### 日志

- 结构化 JSON，包含时间、level、service、version、environment、requestId/traceId、actorId、scope、command、entityId、resultCode。
- 敏感数据脱敏；查看敏感审计日志本身也留痕。

### 指标

- Web/API：RPS、p50/p95/p99、4xx/5xx、超时、实例/事件循环、数据库池。
- 业务：登录失败/锁定、审批积压、待检库存龄期、负库存拒绝、导入失败、发货/付款冲突、对账差异。
- Worker：Outbox pending/oldest age、重试、死信、处理时长、邮件/SMS 成功率。
- 基础设施：RDS CPU/连接/慢查询/存储、OSS 错误、磁盘、证书到期、Nginx 错误。

### 告警

每个告警有 Owner、级别、Runbook、去重/抑制和升级路径。只建仪表盘但无人响应不算通过。

## 10. Gate G：SLO、容量与降级

项目已有 RPO 1 小时、RTO 4 小时目标，但尚缺恢复演练。以下运行目标是 **建议起点，需在试运行规模和业务时段确认后批准**：

| 指标 | 建议起点 | 说明 |
| --- | --- | --- |
| 月可用性 | 99.9% | 排除提前公告的维护窗需业务确认 |
| 交互读接口 p95 | ≤ 500 ms | 不含大导出/文件下载 |
| 核心写接口 p95 | ≤ 1 s | 不含短信/邮件异步送达 |
| 5xx 比例 | < 0.5% | 按服务和关键路由分别观察 |
| Outbox 常态延迟 p95 | ≤ 60 s | 财务/审批通知可设更严格目标 |
| RPO | ≤ 1 小时 | 已有文档目标，必须实测 |
| RTO | ≤ 4 小时 | 已有文档目标，必须实测 |

容量测试必须使用预期 2 倍峰值或经批准的容量系数，覆盖：并发登录、列表查询、导入、发货、付款、Outbox 堆积和大批次回填。实际并发/订单/附件规模在 `05-open-decisions.md` 待确认。

降级原则：

- 邮件、绩效投影不可用时，核心交易可提交并进入 Outbox 重试。
- 短信不可用时，高风险操作应失败关闭，不能降级为客户端确认。
- OSS 不可用时，需要附件证明的发货/财务操作失败关闭。
- 数据库不可用时拒绝写入，不在应用内缓存待写财务/库存命令。

## 11. Gate H：备份、恢复与灾难演练

必须提供：

- RDS 自动备份/PITR 配置、保留期、跨可用区/跨账号策略和加密证明。
- OSS 版本控制/生命周期/误删保护及数据库文件元数据的一致性恢复方案。
- 配置、Nginx、镜像、迁移和密钥轮换记录的恢复方法。
- 生产前必须至少完成一次恢复演练报告：开始/结束时间、恢复点、校验查询、业务抽样、偏差和改进项。
- 上线后的演练频率、覆盖范围和 Owner 由 D-15 批准后固化；“每季度一次”是当前推荐默认，不在批准前冒充既定成本承诺。
- 演练必须验证登录、采购、库存批次、发货、发票、付款、审计与文件能正确关联，不只验证端口可连。

## 12. Gate I：运维与事故响应

- 明确业务 Owner、技术 Owner、数据库/基础设施 Owner、值班和安全联系人。
- 为认证失败、库存对账差异、付款异常、迁移失败、Outbox 堆积、OSS/短信故障编写 Runbook。
- 定义 SEV 等级、升级时限、外部通知、冻结写入和证据保全步骤。
- 管理员 Break-glass 账号双人保管、定期演练、使用即告警并完整审计。
- 发布、回滚、数据修复和人工重放均通过受控命令并记录操作者/原因/结果。

## 14. 上线后保护

- 首批采用小范围工厂/SKU/用户试运行，明确停止条件和业务值守。
- 高风险模块按领域逐步放量；观察错误、延迟、授权拒绝、对账和用户反馈。
- 每日自动对账库存/发货/请款/付款，差异触发告警并冻结相关写入。
- 试运行结束后复盘，再决定扩大范围；不得因“没有用户报错”替代监控与对账证据。
