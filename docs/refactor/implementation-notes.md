# Implementation Notes

## Source

- 用户目标：在已定版基线 `607cb1c` 上准备后端重构，使现有前端与后端分离，并达到可验收、可上线、可运维的生产状态。
- 已批准路径：Fastify + Drizzle/MySQL 模块化单体；Web、API、Worker 独立运行；Nginx 保持同域；以 `/api/v1` 绞杀式迁移现有 Next.js `/api`。
- 本轮范围：只形成业务基线、目标架构、迁移路线、生产门禁与待决策清单，不修改业务代码，不推送、不部署。

## Design Decisions

- 采用 Fastify + Drizzle/MySQL 模块化单体；先建立明确模块所有权与应用服务，不把现有 Next Route 原样搬迁。
- Web、API、Worker 分进程/制品，但经 Nginx 保持浏览器同域；迁移期 `/api/v1` 与旧 `/api` 共存。
- P0 安全和账实一致性问题先在现有系统封堵，不能等待重构自然解决。
- MySQL 8 作为业务语义和集成测试的唯一事实源；停止 D1 类型强转和正则生成生产 Schema 的路线。
- 生产、质检、库存虽然是独立模块，但必须作为同一迁移/UAT 波次，防止待检资产继续断链。
- Purchase Receipt 归 Procurement，并与 Quality/Inventory 在同一 Unit of Work 中编排，补上采购物料进入库存的权威入口。
- 审批只拥有工作流和职责分离；业务副作用由领域 Handler 在同一事务中执行。
- 新旧后端共同校验数据库 writer fence/epoch，幂等使用跨 URL 的 canonical command identity；首次 v1 写入后不再默认允许切回 legacy writer。
- API 与 Worker 复用 `packages/modules/*` 的领域/application 实现，Worker 不复制规则或直接写业务表。
- P0 按“隔离底座入口、领域切写、完整生产”分层关闭，并通过阶段 × Gate 矩阵处理 N/A，避免路线图自锁。
- 文档明确区分仓库事实、推断、建议和待确认事项，历史“已生产”声明不作为本轮重新验证的证据。

## Deviations

- 未偏离已批准的范围：本轮只写重构准备文档，没有修改业务代码、生产配置或外部环境。
- 在原六份规划文档之外增加本 `implementation-notes.md`，用于满足多阶段任务的审计记录；它与规划文档同目录并纳入本地提交。
- 审计补充了当前实现范围，但独立质询指出“仓库没有实现”不能等同于 Sponsor 已批准排除；因此新增 D-00，将 MES、财务、物流、销售/预测与 AI 的目标范围保留为显式决策。
- 独立质询首次判定“需重做”，主会话接受其 P0/P1 并进行一次有界修订；定点复核后判定提升为“有条件接受，可作为实施准备基线”。

## Tradeoffs

- 同域分离降低 Cookie/CORS/CSRF 同时改造的风险，但外部看来仍使用一个域名；进程、源码、契约和发布边界才是本阶段的分离标准。
- 服务端 Session 保留实时吊销能力，代价是 API 需要会话查询；暂不引入 JWT 的密钥轮换和撤销复杂度。
- 单库事务 + Outbox polling 比微服务/MQ 更易保证库存与付款一致性，代价是需要严格的模块导入规则和共享数据库治理。
- 逐领域 Strangler 可回切、风险较低，代价是迁移期需要维护新旧契约和路由清单。
- 暂缓整体移动现有 `app/`，先让新 API/Worker 独立运行，以减少目录重排噪音；最终仍要求 Web 不导入 DB 或服务端业务代码。
