# 迁移路线图

## 1. 迁移策略

采用按领域切换的 Strangler 路线，避免一次性重写：

```text
先控制现有风险
  → 建立新后端底座与契约
  → 迁低风险读接口
  → 迁主数据和导入
  → 迁采购
  → 联合迁生产/质检/库存
  → 迁物流/财务
  → 收口审批/Worker
  → 前端目录与部署彻底独立
  → 下线旧 API
```

五条硬规则：

1. **风险按作用域封堵**：正在承载真实流量的 P0 立即关闭入口或修复；业务闭环 P0 必须在对应领域首次切写前关闭，不用“全部 P0 清零”制造不可达循环。
2. **契约先行**：迁移接口前先保存 v0 行为、定义 v1 契约和 UAT，不把偶然返回结构当成契约。
3. **服务端单一写入者**：一个业务命令只能由旧或新后端之一执行；新旧处理器共同校验数据库 writer fence/epoch，前端开关和 Nginx 不作为所有权证明。
4. **可回切不等于可撤销业务**：首次 v1 写入前可以安全回切；首次写入后默认冻结、向前修复或由当前领域版本补偿，不能假定 legacy 仍可写。
5. **决策先于受影响模型**：开放决策必须绑定首次受影响阶段；没有批准记录就不能开始对应 API/Schema 的正式实现。

## 2. 迁移控制面

每个迁移单元必须维护一条 Manifest：

| 字段 | 内容 |
| --- | --- |
| 领域/用例 | 例如 `inventory.reserve`，不能只写“库存接口” |
| Canonical command | 与 v0/v1 URL 无关的命令类型、聚合 ID 和请求规范化规则 |
| v0 路径 | 当前 Next Route |
| v1 路径 | 新 Fastify Route |
| 读/写所有者 | `legacy/v1/blocked`、当前 writer epoch、切换时间和批准人 |
| 数据表所有者 | 该用例允许写的表 |
| 契约版本 | OpenAPI 版本、前端 Client 版本 |
| 幂等/并发策略 | Idempotency Key、版本条件、唯一约束或锁 |
| 测试证据 | 单元、契约、MySQL 集成、权限、并发、UAT |
| 观察参数 | 观察时长、最小样本量、差异容忍、日志覆盖率和排除流量 |
| 切换协议 | 禁写、排空、对账、递增 epoch、启新写、旧入口拒写探针 |
| 暂停/回滚条件 | 错误率、延迟、对账差异、业务异常阈值及责任人 |
| 证据链接 | Git SHA、镜像/DB 摘要、fixture、命令、报告、UAT/批准记录 |
| 删除条件 | 调用归零、兼容窗结束、恢复演练完成 |

Manifest 应进入版本库并由 CI 校验，但本轮只定义规则，不创建实现台账。

### 写入切换协议

```text
legacy writer
  → writer_fence=blocked
  → 排空旧请求 + canonical command/账实对账
  → epoch+1, owner=v1
  → 开启 v1 写流量
  → 持续证明旧入口返回 409/410 且不落库
```

旧、新入口必须共享 canonical command identity 和幂等作用域。若 v0 已提交但响应丢失，v1 重试必须返回同一结果，不能因 URL 不同生成第二个业务效果。

### 回滚等级

| 等级 | 条件 | 允许动作 |
| --- | --- | --- |
| R0：首次 v1 写入前 | 仍处于 blocked/验证期 | 对账后把 owner 恢复 legacy，回切路由 |
| R1：首次 v1 写入后且兼容 | legacy 已证明能读取/处理新事实 | 先 blocked、排空、对账，再显式批准回切 |
| R2：首次 v1 写入后不兼容 | 高风险领域默认情况 | 冻结写入，部署最后兼容 v1 或向前修复；legacy 不再成为 writer |
| R3：事实需纠正 | 已产生库存/财务/审批记录 | 当前领域版本执行带审批、Step-up、幂等和审计的 compensating command |

### 决策到首次受影响阶段

| 决策 | 最晚批准点 | 必须更新的产物 |
| --- | --- | --- |
| D-00/D-01/D-02/D-03/D-04/D-05/D-09 | 阶段 0 出口 | 产品范围、组织/角色、UAT、目标架构 |
| D-12/D-17A | 阶段 4 入口 | 主数据/导入 Schema、API、文件架构与测试 |
| D-06/D-10（并复用 D-02/03/04/12） | 阶段 5 入口 | Procurement、Purchase Receipt、法律主体、导入 commit |
| D-05/D-06/D-07/D-11/D-12/D-13/D-17A | 阶段 6 入口 | Receipt/Quality/Inventory/Manufacturing 状态机与 UAT |
| D-08/D-10/D-11/D-13/D-16/D-17 | 阶段 7 入口 | Logistics/Finance/Receiver/通知/审计契约 |
| D-14/D-15/D-16/D-17/D-18 | 生产试运行前 | SLO、容量、灾备频率、合规、AI 范围与发布门禁 |

任何 `N/A` 或沿用默认建议都必须有决策人、日期和适用范围，不能用沉默代替批准。

## 3. 阶段 0：业务与生产事实冻结

### 目标

把“现有代码看起来支持什么”和“业务真的需要什么”分开，建立迁移可比较的基线。

### 工作

- 业务方确认角色、组织、工厂/供应商关系、主链状态机和异常处置。
- 标记每个页面为真实、部分、演示或不可用；演示入口不得对试运行用户暗示已完成。
- 保存现有 `/api/*` 请求/响应样本、错误行为和调用方；敏感字段先脱敏。
- 准备一套可重复的匿名 UAT 数据：至少两个工厂、两个供应商、两个仓库、成品/物料 SKU、跨批次库存、发票与付款。
- 盘点真实生产 Schema、`__drizzle_migrations`、DMS 人工变更、数据量和脏数据。
- 明确外部数据源（例如领星）与本系统的权威边界。

### 入口

- 基线提交可追溯；当前代码和环境清单可读。

### 出口

- `01-business-baseline.md` 和 `05-open-decisions.md` 中所有 A 级“实现前阻塞”问题有责任人、批准结论和决策记录。
- 主链、异常链和正式角色矩阵获得业务 Owner 签字。
- 生产 Schema 差异报告完成；没有未登记的人工结构变更。
- UAT 数据集和期望对账结果可重复创建。

### 回滚

- 本阶段不切流量。若业务结论不完整，停留在现状，不开始领域迁移。

## 4. 阶段 1：现有系统紧急止血与生产基线

### 目标

先关闭正在暴露的高风险入口，再建立可信生产 Schema 基线；本阶段不要求提前完成阶段 6 的生产/质检/库存业务闭环。

### 工作

1. 先做不依赖 Schema 的配置/代码止血：禁用生产 Header fallback；Nginx 清除身份断言头；无法安全验证的高风险财务/审批写入口先 fail closed。
2. 在任何 DDL 前只读盘点生产 Schema、迁移历史和 DMS 人工变更，建立签字差异报告。
3. 仅通过向后兼容 Expand 迁移加入 Step-up grant、writer fence、幂等/唯一约束所需结构，并在脱敏生产副本验证。
4. 财务、审批和角色管理改为消费绑定交易意图的一次性 Step-up；建立临时但完整的 workflow 权限策略。
5. 调拨、发货、付款和审批加入原子状态转换、业务唯一约束与 MySQL 并发测试；未通过前保持对应写入口关闭。
6. 删除 D1→MySQL 类型强转，使现有写路径接受真实 MySQL 编译/集成检查。
7. Excel 上传解析在最小 Worker 就绪前对外关闭；若业务必须保留，仅允许受控管理员离线隔离处理，不在 Web 请求进程解析未知文件。

### 入口

- 阶段 0 的角色矩阵、Schema 盘点和测试数据已就绪。

### 出口

- SEC-001 已关闭；SEC-002、AUTHZ-001、CONSISTENCY-001 对仍开放的真实写入口已关闭，否则该入口保持禁用。
- MIG-001 的生产 Schema/迁移基线已签字；所有本阶段结构变更均为兼容 Expand，并完成应用回切演练。
- DEP-001 获得临时关闭证据：不可信 Excel 入口关闭或被证明确实运行在资源隔离环境；永久关闭要在最小 Worker 上线后完成。
- 真实 MySQL 8 跑通登录和仍开放的核心写路径；伪造身份、伪造 Step-up、自审、跨组织访问及并发重放测试通过。
- BIZ-001/BIZ-002 可以保持未关闭，但任何依赖它们的生产/质检/库存新写流量仍禁止开放。

### 回滚

- 仅允许回滚到仍包含安全修复且兼容新 Schema 的版本。
- 财务/库存数据使用追加冲正或修正，不恢复数据库快照覆盖已发生交易。

## 5. 阶段 2：新后端底座

### 目标

建立一个可独立构建、测试、部署但尚不承载高风险写流量的 Fastify API 与 Worker。

### 工作

- 建立 pnpm workspace、`apps/api`、`apps/worker`、`packages/contracts/database/platform/test-support`。
- 建立 `packages/modules/*`，让 API 和 Worker 复用同一领域/application 实现，禁止 Worker 直接写业务表。
- 配置 Fastify 插件生命周期、运行时 Schema、OpenAPI、统一错误、requestId、日志和健康检查。
- 建立 MySQL Unit of Work、显式 MySQL Schema、writer fence、canonical idempotency、迁移检查和 Transactional Outbox。
- 新 API 读取现有 Session；实现统一 ActorContext、角色和数据作用域 Policy。
- 建立审批内核和 `ApprovalEffectHandler` 契约；各领域在自己的迁移阶段交付 Handler，阶段 8 只做旧路由清退。
- 建立最小 Worker：Outbox claim/heartbeat/retry/dead-letter 与资源受限文件解析；后续阶段只扩展消费者。
- CI 执行锁文件安装、lint、typecheck、单元、契约、MySQL 集成、迁移、依赖审计和镜像构建。
- Nginx 增加 `/api/v1/*` 路由，但仅开放健康检查和内部验证接口。
- 统一开发脚本的 Windows/Linux 行为，避免依赖 POSIX 环境变量前缀；本地一条命令可启动 MySQL、Web、API 和 Worker。

### 入口

- 阶段 1 的安全/迁移止血出口已满足；生产 Schema 基线可信。BIZ-001/BIZ-002 等领域切写 P0 不阻止在隔离开发环境搭底座。

### 出口

- Web、API、Worker 可独立构建与启动。
- OpenAPI 能生成 Client；示例接口通过契约和权限负向测试。
- liveness/readiness、结构化日志、指标和 Trace 在 UAT 可观测。
- 空载、故障依赖、优雅停机和数据库池耗尽行为有测试证据。
- Writer fence 能在 legacy/v1/blocked 间切换；旧入口拒写和跨路径幂等反例测试通过。
- 最小 Worker 能在进程重启/重复 claim 下不重复消费，并能隔离解析恶意/超限文件。
- 不切业务写流量。

### 回滚

- 移除 `/api/v1` 路由即可；旧系统不受影响。

## 6. 阶段 3：IAM 与低风险只读查询

### 目标

先证明新 API 能正确复用身份、执行数据范围、生成契约并与旧接口对比。

### 建议用例

- `/session`、当前用户与有效角色。
- 工厂/仓库/SKU/BOM/供应商的作用域内只读查询。
- 文件元数据查询，不先迁上传和敏感下载。

### 方法

- 前端新增单一 `apiClient`，禁止新组件直接 `fetch('/api/...')`。
- 优先录制脱敏请求，在只读生产副本离线重放新旧 GET。若必须在线影子读，先实现显式 shadow context，硬性禁止 Session/角色刷新、审计、提醒及任何业务写入；当前 GET 会更新会话/角色并写审计，不能直接复制生产请求。
- 差异区分为 v0 bug、v1 bug、契约明确变化，不追求错误行为的盲目兼容。

### 出口

- 正式角色矩阵的可见/不可见样本全部通过。
- Manifest 中批准的观察时长、最小样本量、字段差异容忍、日志覆盖率和排除流量均满足，且无未解释差异。
- 前端可在配置开关下切换新 Client；Session 与登出行为一致。

### 回滚

- 前端或 Nginx 回切 v0 GET；不涉及数据补偿。

## 7. 阶段 4：主数据、供应商与通用导入管道

### 目标

先迁后续交易依赖的稳定主数据，并建立不越过领域所有权的通用导入管道。

### 范围

- 工厂、仓库、SKU、单位换算、BOM 版本与有效期。
- 供应商、供应商-SKU、产能、价格协议和价格审批。
- 五类文件的 upload→parse→stage→map→validate；本阶段只允许 Supplier/Master Data 拥有的供应商、SKU 完成领域 commit。
- 采购计划/采购单 commit 延后到阶段 5 并调用 Procurement；期初库存 commit 延后到阶段 6 并调用 Inventory。
- 文件 Upload Session、扫描/隔离和业务附件绑定。
- 交付 Supplier/Master Data 的 ApprovalEffectHandler；旧审批路由不得直接写已迁移表。

### 入口决策

- D-12（价格、单位、容量、容差）和 D-17A（文件驻留/加密/WORM/大小等架构约束）已有批准记录。

### 关键不变量

- 业务键唯一；生效版本不能非法重叠。
- 单位换算和金额精度由服务端验证。
- 导入批次可追踪、可重试、不重复提交，不允许部分成功却标记 `committed`。
- 采购使用的 BOM/价格必须能形成不可变快照，后续主数据修改不改变历史交易。

### 出口

- 五类导入均完成 upload→parse→stage→map→validate；供应商/SKU commit 完成，采购与期初库存明确显示“待所属领域启用”，不得伪装提交成功。
- 重复文件、重复业务键、部分坏行、大文件和恶意文件场景通过。
- 权限矩阵中标记为“需要审批”的主数据写入均有审批、作用域和审计测试，不把所有主数据操作无意升级为审批。
- 旧主数据写接口调用归零后进入兼容观察期。

### 回滚

- 写路由回切前确认新旧版本都兼容扩展字段。
- 已创建的主数据不物理删除；通过停用/新版本修正。

## 8. 阶段 5：采购领域

### 目标

迁移采购计划、工厂确认、采购单和计划分配，并在服务器端强制价格/BOM/容差规则。

### 范围

- 采购计划版本、来源行、工厂级响应和超时。
- 采购单、计划明细分配、工厂级确认、交期异议和偏差审批。
- 已审批价格、生效期、供应商-SKU 关系、产能与 BOM 快照。
- Purchase Receipt 聚合、状态机和跨模块端口；本阶段可建立契约/数据结构，但对真实库存的收货切写随阶段 6 联合启用。
- 采购计划/采购单导入的 domain commit，由 Procurement application service 执行。
- 交付 Procurement ApprovalEffectHandler，旧审批路由不得写已迁移采购表。

### 前置业务决定

- D-02/D-03/D-04/D-06/D-10/D-12 已批准：组织关系、多工厂聚合、外部权威、采购收货、法律主体和价格/容差规则确定。

### 出口

- 单工厂、多工厂、部分确认、无法履约、超计划、欠计划、版本边界场景通过。
- 客户端不能注入未审批供应商或价格。
- 同一导入/创建命令重试只产生一个业务结果。
- 新旧读取对账完成，采购写所有权切至 v1。
- Purchase Receipt 契约和 `Receipt→Quality→Inventory` 联合 UAT fixture 就绪，但尚未对真实库存开放。

### 回滚

- 按 R0–R3 回滚等级处理；首次 v1 采购写入后，legacy 只有在明确兼容证明和 writer fence 切换后才能恢复写入，否则保持只读并向前修复。

## 9. 阶段 6：生产、质检与库存联合波次

### 目标

补齐系统最核心的实物链路，使每一次预留、领料、完工、质检和处置都可对账到具体批次。

### 必须共同交付的状态链

唯一规范状态机见 `01-business-baseline.md` 第 6.2 节，必须完整覆盖 `MaterialShortage`、部分/全部预留、`VariancePending`、审批驳回、待检、放行、隔离和各处置去向。本路线图不再维护一份删减版状态机。

### 入口决策

- D-05/D-06/D-07/D-11/D-12/D-13/D-17A 已批准：试点、采购收货/领料、质检粒度、历史数据、数量/容差、不合格处置和文件架构约束确定。

### 内部增量（不分别宣布业务完成）

1. 建立 Inventory ledger、预留、批次来源和并发原语，暂不开放外部写入口。
2. 激活 Purchase Receipt→来料质检→待检批次→放行/隔离，并让期初库存导入通过 Inventory commit。
3. 接入 Manufacturing 的真实预留/领料/消耗/完工，再接入成品质检与处置。
4. 在联合维护窗将相关 command writer fence 置 blocked，排空、全链对账后协调切至 v1。

### 工作

- 生产单保存 BOM 快照；真实创建库存预留，支持部分预留、缺口、释放、优先级和消费。
- Purchase Receipt 作为采购物料入库入口，创建来料质检任务和有来源的待检库存批次。
- 领料/消耗/损耗写不可变库存流水，并校验数量守恒。
- 完工创建有来源的待检批次；质检必须绑定具体 `inventoryBatchId` 或等价批次标识。
- 抽检失败触发全检/处置；支持按数量拆分放行、返工、退回、报废和让步接收。
- 调拨、盘点、效期冻结和 FEFO 全部经过 InventoryApplicationService。

### 出口

- 理论用量、预留、领用、消耗、损耗、完工、待检、可用、隔离、次品总量可逐笔守恒。
- 采购累计收货、来料质检和物料待检/可用/隔离逐笔守恒，UAT-REC-01 通过。
- 并发预留/释放/消费、重复完工、重复质检、调拨重放不产生负数或重复批次。
- 生产批次到质检与库存处置具有完整追踪链。
- 真实仓库盘点能从流水重建余额并解释差异。

### 回滚

- 联合切写前可按 R0 回退；首次 v1 实物写入后默认进入 R2，冻结相关命令并部署兼容 v1/向前修复，不能把旧生产、质检或库存接口单独恢复为 writer。
- 已提交的实物变更走版本化 compensating command，生成反向库存流水并经过权限/审批/幂等/审计，不删除记录。

## 10. 阶段 7：物流与财务

### 目标

在可信库存基础上迁移发货、签收、退货、请款、发票与付款。

### 范围

- 发货计划、实际发货、凭证、日期偏差、FEFO 扣库。
- 收货方主数据/账号作用域、签收、少货/破损、物流异常。
- 退货冻结、质检、返工/退回/报废处置。
- 发货生成付款计划/请款；发票登记、双核、占用、部分付款、红票/作废、补票、退款与冲正。
- 交付 Logistics/Finance ApprovalEffectHandler，并关闭旧审批路由对这些表的直接写入。

### 入口决策

- D-08/D-10/D-11/D-13/D-16/D-17 已批准：收货方、法律主体、历史数据、处置后果、通知和文件/审计规则确定。

### 关键不变量

- 同一发货批次只能完成一次有效发货、扣库和请款派生。
- 已付合计不得超过请款可付金额；发票占用合计不得超过有效票额。
- 付款、高风险更正和风险解除必须原子消费绑定对象版本与 canonical request hash 的 Step-up Proof。
- 财务原记录不可覆盖，所有更正可追溯到原记录和审批。

### 出口

- 发货重试、并发发货、部分签收、少货、破损、退货和补偿场景通过。
- 并发付款、重复银行流水、跨请款分配、红票/补票/退款场景通过。
- 库存、物流、请款、发票、付款可按批次/单号端到端对账。
- 财务和外部角色数据范围测试全部通过。

### 回滚

- 按 R0–R3 判断；首次 v1 财务/库存写入后默认不回切 legacy writer，使用兼容 v1 或向前修复。
- 如发生对账差异，立即停止新写流量，保留读与审计，不自动重放未知结果命令。

## 11. 阶段 8：审批旧路由、Worker 与横切能力收口

### 目标

在各领域 Handler 已随阶段 4–7 迁移的前提下，删除跨域审批写入，并把剩余后台任务迁到阶段 2 建立的可靠 Worker。

### 工作

- 核对所有 workflow 均已注册领域 Handler，随后移除旧审批路由对跨域表的直接写入。
- 迁移剩余审计归档、提醒、通知、邮件、效期扫描和绩效投影到 Outbox/Worker；文件解析已在阶段 2 建立，阶段 4 只扩展业务处理。
- 对阶段 2 的原子 claim、租约、幂等消费者、退避、死信、积压指标和人工重放做全消费者复核。
- 关键审计使用追加权限与不可变归档策略。

### 出口

- 每种工作流的可见角色、审核角色、职责分离、高风险要求和副作用均有测试。
- 审批失败不会留下“状态已通过、业务未生效”。
- Worker 重启、重复消费、下游超时和永久失败均有演练；通知不会静默丢失。
- 旧 HTTP 定时任务入口关闭或只保留受控运维触发。

### 回滚

- 暂停 Worker 消费但保留 Outbox；恢复后按幂等语义继续。
- 不把事件状态回退为未发生；失败使用重试或人工补偿。

## 12. 阶段 9：Web 独立与旧系统下线

### 目标

完成源码、构建、部署和运维上的真正前后端分离。

### 工作

- 将现有前端收敛到 `apps/web`，删除数据库和服务端业务依赖。
- 所有组件只通过生成 Client/前端 API Facade 访问 `/api/v1`。
- 按角色返回后端 Capability，前端导航以 Capability 呈现，但仍不替代后端授权。
- 静态演示页面要么接入真实 API，要么明确标记/移除。
- 按 Manifest 参数统计旧 `/api/*` 调用；在删除前完成全量 UAT、性能、故障、应用回切和 RDS/OSS 恢复演练。
- 只有删除门禁全部通过、兼容窗结束后，才删除旧 Route Handlers 和 D1 业务适配；删除后再跑一次最终回归，不把它冒充首次恢复验证。

### 出口

- Web/API/Worker 独立镜像、独立健康、独立扩缩、独立回滚。
- 生产访问日志证明旧 API 在兼容窗内无调用。
- 所有 v1 契约消费者已登记且兼容测试通过。
- 删除前恢复/回切演练证据完整；删除后最终回归通过。

### 回滚

- 保留最近兼容镜像和 Nginx 路由配置；数据库 Schema 仍兼容回滚窗口内版本。
- 旧 Route 源码删除只在恢复窗口结束后进行，删除提交可追溯。

## 13. 阶段 × Gate 适用矩阵

不是所有 Gate 都适用于每个阶段。`N/A` 必须写明理由和批准人；不能为了让阶段变绿而省略本来适用的门禁。

| 阶段 | 业务/UAT | OpenAPI/Client | DB/迁移 | CI/可观测 | Writer fence/切流 |
| --- | --- | --- | --- | --- | --- |
| 0 事实冻结 | 决策签字、fixture/oracle 定义 | N/A：尚未建 v1 | 只读 Schema 差异报告 | 基线扫描证据 | N/A：不切流 |
| 1 紧急止血 | 受影响用例负向/并发验收 | legacy 契约样本 | 仅已批准 Expand；生产副本验证 | 安全/迁移 CI 证据 | 写入口关闭/恢复探针 |
| 2 平台底座 | N/A：无领域写流量 | 必须 | 空库/副本/重入验证 | 必须；日志/指标/Worker | fence 自测，仍不切业务写 |
| 3 只读查询 | 角色/作用域读 UAT | 必须 | 只读模型相关迁移才适用 | 必须 | 读切换；无写 owner 变化 |
| 4–7 领域迁移 | 仅受影响领域的正常/异常 UAT | 必须 | 有变更则空库+副本+兼容回切 | 必须覆盖新增故障 | 必须执行 blocked→排空→epoch→v1 |
| 8 横切收口 | 工作流/Worker 故障与重复消费 | 有契约变更则必须 | 有变更则必须 | 全消费者必须 | 旧审批/Job 入口拒写/关闭 |
| 9 清退/生产 | 全链 UAT、性能、故障、恢复 | 全消费者兼容 | 删除前恢复；Contract 另批批准 | 完整发布证据 | 旧入口零调用且拒写 |

所有阶段真正共有的条件只有：本阶段适用的 P0 已关闭；所需决策已批准；Manifest/证据包完整；失败路径和资源去向明确。详细标准见 `04-production-gates.md`。

## 14. 可复现证据包

每个发布候选生成不可变 evidence bundle，至少包含：

- release ID、Git SHA、Web/API/Worker 镜像摘要、依赖锁文件与 SBOM 摘要；
- MySQL 版本/镜像摘要、Schema manifest、迁移 checksum、备份/恢复点标识；
- fixture/seed 版本、业务 oracle 版本、脱敏规则和可重复执行命令；
- 单元/契约/MySQL/权限/并发/Worker/E2E 报告（机器可读结果 + 摘要）；
- 影子/离线回放参数、样本量、差异结果、日志覆盖率与排除项；
- 性能/故障/恢复报告、实际 RPO/RTO、监控截图或查询链接；
- UAT 签字、风险例外、批准人、writer epoch 切换记录和回滚/补偿演练结果。

敏感生产数据不进入 Git；仓库中的 release manifest 只保存受控证据存储的内容摘要和不可变链接。没有固定 fixture、oracle、命令和环境摘要的“手工看起来正常”不算完成证据。

## 15. 暂停与升级条件

出现以下情况，停止切写并回到主决策：

- 业务状态机或法律/财务主体出现两种实质不同解释。
- 发现真实生产 Schema、数据量或外部系统所有权与基线冲突。
- 同一 P0 在两轮修复后仍不能通过相同完成证据。
- 需要双写、跨数据库事务、跨站身份或拆微服务才能继续。
- 迁移会破坏已发布接口、不可逆数据或恢复目标。
- 生产错误率、延迟、对账差异或授权拒绝超过已批准阈值。

## 16. 排期方式

本路线图刻意不写绝对工期。工期必须在以下输入确认后估算：

- 正式团队人数和 Fastify/MySQL/测试能力。
- `05-open-decisions.md` 中实现前阻塞项的答案。
- 真实生产 Schema、历史数据量、活跃用户和接口调用量。
- 首批试运行工厂、SKU、订单规模与 UAT 签字人。
- 目标 SLO、RPO/RTO 和合规要求。

估算单位应以“可独立验收的用例/迁移波次”为主，不以 Route 文件数量为主。
